### 两种练法与 100LS 的对应关系（回答"为什么这样替代"）

| 100LS 原方法的要素 | 本项目的替代 | 差异 |
|---|---|---|
| 一部电影听 100 遍 | 同一批 10 句听 3 轮 | 素材零门槛、一次会话做得完 |
| 无字幕 → 中文字幕 → 英文字幕 | 盲听 → 看中文 → 看英文 | 梯度保留 |
| 反复听到脱口而出 | 同一句可无限次「再听一遍」 | 不设次数目标 |
| 完成后…？ | 落一次 session，不改 FSRS | 「听过」不等于「会了」 |

另一条做了机制化的是**完形**：它把「在句子里用对」这件事变成可判定的单空题，
答案精确对应一个词条，所以能干净地接进 FSRS（答错进错词本）。

### 这一轮实测出来的三条数据（会反复被引用）

1. **99.0%** 的例句里目标词以原形或屈折形式出现（21.2% 只有屈折形式）
2. **98.8%** 的目标词在句中**恰好出现一次**；重复出现的 0.3% 会泄露答案，整句弃用
3. **540 个短语词条**（pencil box / living room），匹配必须按词序列

### 已知限制（不是 bug，别去"修"）

- `brown → Ms. Brown` 这类**同形专有名词**会被挖，语义已偏离词条本义。
  这类占 1.35%，但仍能练到正确词形，**决定不改**——加大小写规则会把引号后句首大写
  的 `"She likes music."` 也误伤，净收益是负的。
- 完形不挖派生词（fold→folder、hard→hardly），因为那会考到别的词条。

## 五、环境注意（HANDOVER 有详述，这里只挑新的）

### 推送：这次又多踩了两次
M HANDOVER 五.1 已记录「会有整条 github.com:443 不通的时段」，**11-21 14:26–14:35 又遇到一次**，
新增两条判断线索（已写进 HANDOVER）：

1. **分清 TCP 与 TLS**：`/dev/tcp/<ip>/443` 全部 `TCP OK`，但 `curl https://` 全部 `000`
   → 端口通、TLS 被 RST，**换 IP 无意义**
2. **用 80 端口做对照**：同一 IP 的 `http://` 返回 **301** 正常，`https://` 返回 000
   → 确认是 TLS 层被掐。用 `curl -L` 跟随那个 301 跳回 https 反而可能拿到 200（握手时好时坏）

**策略**：隔几十秒探一次，一探到 200 立刻 push；不要一失败就改命令或换方案。
可用 IP 池会变：`140.82.112.4` / `.113.4` / `.114.4` / `.116.4` / `.121.4`（`.3` 系列基本不通）。

`ssh.github.com:443` 与 `github.com:22` 两次都通，但 `~/.ssh/` 没密钥 —— 配 SSH key 可绕开这个干扰。

### 其他地方照 HANDOVER 第五节做，重点是三条红线
1. 推送必须带 `-c credential.helper=` 先清空（`-c` 是**追加**不是替换）
2. 改源码只用 Edit/Write，禁 `sed -i`/`python -c`/超长 `node -e`
3. 桌面版只换 `resources/app/dist`，**绝不换 `main.cjs`/`preload.cjs`**（换 origin 会让用户学习进度不可见）

### 窄式听为什么用「整篇文章」而不是词汇聚类（实测结论，别再重做）

原本打算按词汇相似度把例句聚成主题批次。**实测否掉了**：

| 量测 | 结果 |
|---|---|
| 同一篇文章内部，任意两句平均共享内容词 | **0.11–0.36 个** |
| 跨文章随机两句 | 0.06 个 |
| 按重叠度贪心聚出的簇 | 聚在 `own` / `like` / `dont` 这类高频词上，簇内混进重复句 |

结论：真正的同主题文本，词汇重叠本来就极低——**用重叠度区分不出主题**。
数值上「提升 68 倍」只是基线接近 0 造成的假象。改为一篇 = 一个批次，
直接拿到「同作者 / 同主题 / 同语域」，不需要任何算法。
