## 二、做了什么

### 第一步：先核实，再动手

接手时 `docs/unimplemented-features.md` 和 README 都写着「收藏没接调度」「自定义文章导入没做」「报告导出没做」「词库众包未开始」。逐条对照源码后发现**四条里三条早已实现、一条已被 revert**：

- 收藏已接调度（`src/data/round.ts:125-152` 有 `favNotDue` 插队通道）
- 自定义文章导入已实现（`src/data/customArticles.ts` 22KB + 33 个单测）
- 报告导出已实现（`src/lib/report.ts` 已接进 `StatsPage`，可导出 SVG / 打印 PDF）
- 词库众包实现后已 revert，代码无残留

先花时间做这件事的理由：**文档写得比代码多，会让接手的人重复做已完成的工作**。核实完才重写文档，把真实缺口列出来。

### 第二步：四项功能

**① tem8 放开截断（5f2e78f）**

`scripts/build-more-dicts.mjs` 里给 tem8 写了 `limit: 8000`，但源文件 `Level8luan_2_T.json` 有 12,197 条。删掉 limit 后重建：11,858 词（丢 339 条空释义、去重 0 条）。

关键是**截断的隐患不是"少了 3,858 个词"，而是"按源顺序取前 N 条"**——源顺序不等于难度顺序，截断后末词停在 `slime`，`ab-`、`su-` 开头的词大量缺失。这种缺失在 UI 上完全看不出来，用户只会觉得"这个词怎么没有"。

体积从 2.23MB 涨到 2.87MB（gzip 1.12MB / brotli 734KB）。不担心首屏是因为词库**按需 fetch**：进哪个词库才下载哪个，首屏一个词库都不加载。

**② 文章译稿进仓库 + 点词查释义（b67d375、741aec0）**

译稿原先放在 `.tmp/articles-work/`——而 `.tmp` 是 gitignore 的。也就是说**别人 clone 下来根本跑不出文章**。移了 8 个文件（classics.json + zh-batch-01..07.json，共 132KB）到 `data/articles-work/`，`.tmp` 里剩下的 16MB 是试验脚本与中间产物，不需要进仓库。

点词是这几项里最花时间的。难点不在 UI，在**词条数据从哪来**：

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| 运行时查 16 个词库 | 点一个词要下整库：gaokao 1.3MB / tem8 2.87MB | 不可接受 |
| 预生成 gloss 文件（全量 WordEntry） | 481KB raw / 259KB gzip | 太重 |
| **预生成精简 gloss（1 条例句）** | **294KB raw / 120KB gzip** | **采用** |
| 不预生成，只查已加载的词库 | 用户没进过词库时点词全空 | 体验断崖 |

最终产物 `public/dicts/article-glossary.json`：1,449 个原形 + 554 个词形变体，只覆盖文章里出现过的词。词形解析链处理了 `think?'`、`machine'` 这类切词残留（去尾撇号 → 去 `n't` → 撇号前段 → 连字符拆分），加上 word-graph 的 `f` 反查原形，覆盖率做到 **98.4% 的 token 命中 / 94.8% 的唯一词命中**。

**③ 句子库练习（3a95167、8a16848）**

把词放回例句里整句输入。三个来源：错词本 / 收藏 / 指定词库，一轮 10 句，Enter 提交后逐词着色。

设计上的关键取舍是**按词对齐而不是按字符对齐**：逐字符比对会把长句打成"红一片"，而且一个词打错后后面全部错位，用户看不出到底错了哪个词。

**④ 错词按类型分组（02f7dab）**

这是唯一需要新数据结构的项。原来 `UserWord` 只有 `mistakes` 总数，看不出错在哪一类。现在按「期望字符 vs 实际按键」归成四类：

| 类型 | 判定 | 用户能读懂的说明 |
| --- | --- | --- |
| `order` | 打的是刚打过的字符，或下一个字符 | 手比眼睛快 |
| `adjacent` | 两个键在键盘上相邻（含上下行斜向） | 手指定位漂了 |
| `similar` | b/d、p/q、m/n 这类镜像或形近对 | 视觉辨别问题 |
| `unrelated` | 其余（含所有非字母输入） | 这个词还没记住 |

优先级从上往下，先命中先归类。分类在 store 的 `input` 里当场算完——因为 `TypingState.lastWrongChar` 只活到下一次按键，期望字符一旦在非严格模式推进光标也拿不回来。**这样 `src/lib/typing.ts` 的接口一行没改，引擎仍是纯粹的字符校验职责。**

## 四、关键技术决策

### 1. 错误分类放 `UserWord` 可选字段，不建新表

直觉做法是新建一张 `mistakeEvents` 表记录每次错误。没这么做，因为：

- 分类是**稀疏**的——只关心"这个词在哪类错上栽过"，不关心第 3 次错和第 7 次错分别是什么
- 一张新表要写 Dexie `version(3)` 迁移，还要在 `clearAllData` / `exportAllData` / `importAllData` 三处同步（这三个函数现在都**没有**覆盖 `customArticles`，是个既有缺陷，再加一张表只会让漏的地方更多）
- 字段可选意味着老记录自动兼容，聚合时按"未分类"处理而不是当成 0——**全零会被读成"从没错过这类错"，那是假的**

### 2. 键盘热力图不做，是因为它和错词分组不是一个数据结构

错词分组能用"词条上的字段"解决，键盘热力图不行：它要统计**所有**键（包括从没打错过的键）的击键分布，那是另一个维度的数据，塞不进词条记录里。真要做得建独立的按键统计表。这条写进了 `docs/unimplemented-features.md` 的 B 档说明。

### 3. 点词用 `span[role="button"]` 而不是 `<button>`

一句话里有几十个可点词，全用 `<button>` 会污染 Tab 焦点漫游——用户按 Tab 是想跳输入框，不是想在几十个单词间挨个跳。用 `span` + `role="button"` + `onClick`，视觉与语义都在，焦点链干净。

### 4. 快捷键集中在 `lib/keys.ts`，改键占用即交换

四个动作（next / replay / backspace / exit）的键位从写死改成读 `Settings.shortcuts`。判定集中在一个 `matchShortcut()` 里，理由：**脏配置（两个动作抢同一键）只能在一处收敛**，散在各处的 `if` 迟早会出现"按一个键触发两件事"。

改键时如果新键已被占用，**交换两个动作的键位**而不是拒绝——改键最常见的场景就是"这两个键我想对调"，一步到位且永远保持合法映射。

字母键不能绑定（空格例外）：绑成 `a` 会让打含 a 的词直接触发，功能坏掉且用户联想不到原因。

### 5. 排版细节：错误分类徽标按固定顺序不按数量

同一行的分类徽标如果按数量排序，每次练习后位置都在变，反而看不出规律。固定按 `order → adjacent → similar → unrelated` 顺序，位置稳定才好扫视。

## 六、从这次接手学到的

**1. 接手别人的项目，先核实文档再动手。** 这次四分之三的"待办"其实早就做完了。如果直接照着文档开工，会重写已有的功能，还会因为"和现有实现冲突"而困惑。

**2. flaky 测试要先验基线，不要先怀疑自己的改动。** `PracticeFlow` 那个随机失败，如果假设是自己引入的，会去查新写的代码——实际先 `git stash` 跑基线，三分钟就确认了方向。

**3. 体积问题要在方案阶段量，不要写完再量。** 点词这个功能试了三种编码才定下来（481KB / 294KB / 120KB 差 4 倍）。先写后量的话，等发现 481KB 太大时实现已经铺开了。

**4. 数据缺失的"量变"往往藏着"质变"。** tem8 少 3,858 个词看起来只是数量问题，实际是"按源顺序截断"导致成片字母段缺失——这是结构性缺陷，只是恰好表现成数量不足。
