- **打字引擎**：逐字符校验、错误不前进（防止错误肌肉记忆）、严格/非严格两种纠错模式

## 四、关键技术决策

### 1. Tatoeba 从 API 改离线 join（提速 500 倍）

原计划逐词请求 API 拿例句。实测：单次 2–10 秒、3 个并发即被限流，13,987 词要 **8 小时**。

改为下载官方导出包离线匹配：
- 英中链接表只有 471KB
- 扫 204 万句耗时 **1 分钟**
- 运行时完全离线，不发任何请求

### 2. Electron 用 `app://` 而非 `file://`

`file://` 下 Chromium 把 origin 视为不透明源，**IndexedDB 直接不可用**，页面永远卡在"正在加载"。

改为注册自定义标准协议 `app://englishmate/`，恢复正常存储语义。

### 3. 难度分级放弃量化指标

试了三种都失败：

| 方案 | 失败原因 |
|---|---|
| ECDICT 词频分位 | 寓言里的古体词（vixen、gnat）把《The Gnat and the Bull》判成雅思 |
| 平均句长 | 1912 年译文句子 78–103 字符，与图灵论文无差别，26 篇寓言误判考研 |
| 从句密度 | 实测寓言 2.2、议论文 1.0，**寓言反而更高** |

结论：结构指标分不开寓言与学术散文，真正的差别是内容抽象度，机器判断不可靠。最终按来源类型定档。

### 4. 放弃 Tatoeba 拼文章

试过按主题组装"文章"，生成结果里混进了 `I'd be unhappy, but I wouldn't kill myself` 这类既无关又不适合学习材料的内容。

根本原因：Tatoeba 是孤立句库，关键词筛出来只是"都含某个词"，不是"讲同一件事"。

**结论：Tatoeba 适合当例句，不适合当文章。**

### 5. 清理历史中的 215MB 误提交

推送前发现 `release/` 打包产物曾被提交（含 215MB exe）。这会导致 GitHub 直接拒收。

用 `git filter-branch` 从全部历史清除，`.git` 从 **169MB 降到 4.9MB**。

## 五、开源合规

三个数据源许可逐一核查并在应用内署名：

| 数据 | 来源 | 许可 |
|---|---|---|
| 词表 | Qwerty Learner | MIT |
| 词性释义 | ECDICT | MIT |
| 英中例句 | Tatoeba | CC-BY 2.0 FR（**需署名**） |
| 文章 | Aesop's Fables（Gutenberg #11339） | 公版 |

1. **TypeWords 是 GPL-3.0** —— 字段最全（例句/短语/词源/双音标全有），但数据拷进 MIT 仓库就是许可传染。只借鉴机制，代码数据全部自己实现。
2. **ipa-dict 的 en_UK 上游是 GPL-3.0** —— 有许可尾巴，只用 en_US。

## 七、诚实的自评

### 做得好的

- **验证密度**：215 个测试 + 真机浏览器驱动 + 逐页截图核对。多个 bug（透明度失效、假开关、假按钮）是看图和跑脚本发现的，不是靠读代码猜的
- **遇到死路会换方案**：Tatoeba API 跑不动就改离线；词频分级不成立就承认并换判据
- **保留证据**：失败方案（Tatoeba 拼文章、量化分级）都写进 docs，没有悄悄删掉

### 需要改进的

- **早期说得太满**：第一版汇报把"14 个成就"列为已交付，实际判定函数从未被调用。后来主动纠正了，但这是不该发生的
- **测试隔离踩坑**：fake-indexeddb 并行互相清库导致偶发失败，排查耗时较久
- **桌面打包没完全解决**：NSIS 安装包始终没跑通，用了替代方案
