# 词库贡献指南

> **不需要会写代码。** 照着做，把一份 JSON 文件交给我们，剩下的由 CI 和审核同学处理。
>
> 本文档面向所有用户。如果你只是想用词库，不用看这些。

EnglishMate 是 MIT 开源项目，内置词库继承自 [Qwerty Learner](https://github.com/RealKai42/qwerty-learner)。你贡献的词库会以 **MIT 许可**并入项目，所有人免费使用。

---

## 一、最快的路子：从 App 里导出

如果你已经在 App 里导入过自己的词表（词库页 →「导入自定义词库」），那么：

1. 打开 **词库页**，找到标着「自定义」的那个词库；
2. 点 **「导出为贡献格式」** —— 会下载一个 `user-xxx.json` 文件，格式已经调好了；
3. 点 **「提交到 GitHub」** —— 会打开一个新建 Issue 的页面，标题和正文都填好了，并且同时把同一个 JSON 文件下载下来；
4. 用记事本 / VS Code 打开那个 JSON，**全选复制**，粘贴到 Issue 正文里 ` ```json ` 和 ` ``` ` 之间的位置；
5. 提交 Issue。维护者会处理。

> 两个按钮都在自定义词库卡片底部的工具栏里。内置词库没有这两个按钮——它们的来源已经固定，无法再次贡献。

走这条路可以**跳过**下面的手写格式部分。但如果你是手写或从别处整理词表，请继续读。

## 二、词库文件的格式

一个词库 = 一个 JSON 文件。结构只有两块：`meta`（词库信息）和 `words`（词条数组）。

```json
{
  "meta": {
    "id": "my-travel-words",
    "name": "我的旅行词汇",
    "category": "basic",
    "description": "出国旅行常遇到的 120 个单词，机场、酒店、点餐场景。",
    "count": 3,
    "source": "本人整理 (MIT) · 词库格式与字段规范沿用 Qwerty Learner (MIT)"
  },
  "words": [
    { "w": "boarding", "t": "n. 登机；上车", "p": "/ˈbɔːrdɪŋ/" },
    { "w": "layover", "t": "n. 中途停留，转机等候" },
    { "w": "checkout", "t": "n. 退房；结账" }
  ]
}
```

上面这份就是**可直接复制的骨架**，把 `name` / `description` / `words` 换成你自己的即可。

### 2.1 `meta` 的六个字段（一个都不能少，也不能多）

| 字段          | 类型   | 说明                                                                     |
| ------------- | ------ | ------------------------------------------------------------------------ |
| `id`          | 字符串 | 词库唯一标识，**必须等于文件名**（`<id>.json`）。只用小写字母、数字、`-` |
| `name`        | 字符串 | 显示名，会出现在词库页，建议 `类别 · 主题` 的格式                        |
| `category`    | 字符串 | **只能取 `exam` / `programming` / `basic` 三选一**                       |
| `description` | 字符串 | 一句话描述，说清「谁适合用、覆盖什么」                                   |
| `count`       | 数字   | **必须严格等于 `words` 数组的长度**                                      |
| `source`      | 字符串 | 出处与许可，见 2.2 —— **这里写错是被拒的第一大原因**                     |

`category` 怎么选：

- `exam` —— 考试词表（四六级、考研、雅思托福、专四专八、GRE、SAT、BEC）
- `programming` —— 编程 / 计算机术语
- `basic` —— 其他一切基础或生活词表（小学、初中、高考、医学、你的旅行词表……）

拿不准就用 `basic`。

### 2.2 `source` 怎么写（硬性要求）

`source` 必须写清两件事：**这份数据从哪来的** + **许可是什么**。

校验脚本对 `source` 有两条机器检查，**两条都必须满足**：

1. 必须包含 `qwerty learner`（不区分大小写）——说明格式与字段规范沿用上游；
2. 必须包含**半角** `(MIT)` ——许可标签。

因此推荐直接照抄这一行，只把最前面的出处换掉：

```text
用户贡献 (MIT) · 词库格式与字段规范沿用 Qwerty Learner (MIT)
```

如果词表来自别处的开源数据，请如实写明并确认其许可允许 MIT 项目使用，例如：

```text
ECDICT (MIT) 释义 · 本人整理 (MIT) · 词库格式与字段规范沿用 Qwerty Learner (MIT)
```

> ⚠️ **注意是半角括号 `(MIT)`，不是中文全角 `（MIT）`。** 校验脚本用的是 `/\(MIT\)/`，全角括号会直接判失败。这是实际踩过的坑。
>
> ⚠️ 不要抄别人的词表却不写来源。许可不明的贡献一律不收——这是为了保护项目，也保护你。

### 2.3 `words` 里每个词条

必填两个字段：

| 字段 | 类型   | 说明                                                |
| ---- | ------ | --------------------------------------------------- |
| `w`  | 字符串 | 单词本身。**首尾不能有空格**，长度 ≤ 64，不能含换行 |
| `t`  | 字符串 | 中文释义。**不能为空**。多条释义用全角 `；` 分隔    |

可选字段 `p`（音标）：如果写，**必须**用斜杠包起来，形如 `/ˈbɔːrdɪŋ/`，长度至少 3 个字符。

不写 `p` 完全没问题。**写了但格式不对，整个词库都会校验失败**，所以拿不准就干脆别写。

还有若干可选富字段（`defs` 词性释义、`sentences` 例句、`phrases` 短语、`synos` 近义词、`relWords` 同根词），属于锦上添花，不影响合并。格式可以看 `public/dicts/` 下任意一个现有词库，例如 `coding.json` 的开头。

### 2.4 词条数量下限

**至少 100 条。** 少于 100 条会被 CI 直接判失败。

小词表不是没价值，但更适合作为**现有词库的内容补充**（补充释义、例句、音标）提交，而不是新建一个词库。

## 三、提交流程（GitHub PR 路线）

如果你有 GitHub 账号，走这条正式路线：

### 第 1 步：Fork 仓库

打开 <https://github.com/2327192084/englishmate>，点右上角 **Fork**。

### 第 2 步：放文件

在你的 fork 里，把词库文件放到 **`public/dicts/`** 目录下，文件名必须是 `<id>.json`。

例如 `id` 是 `my-travel-words`，文件名就是 `my-travel-words.json`。

### 第 3 步：更新索引（这步别漏）

打开 `public/dicts/index.json`，在 `banks` 数组**末尾**加上你这个词库的 meta —— **和文件里的 `meta` 一字不差**（同样的字段、同样的顺序）：

```json
{
  "id": "my-travel-words",
  "name": "我的旅行词汇",
  "category": "basic",
  "description": "出国旅行常遇到的 120 个单词，机场、酒店、点餐场景。",
  "count": 120,
  "source": "用户贡献 (MIT) · 词库格式与字段规范沿用 Qwerty Learner (MIT)"
}
```

同时把顶部的 `generatedAt` 改成当前 UTC 时间，格式照旧（形如 `2026-11-19T10:03:07.444Z`）。

> 校验脚本会逐字段比对「索引里的这一条」和「文件里的 `meta`」，字段顺序不同也会报错。**最稳的做法是从文件里复制粘贴，不要手打。**

### 第 4 步：提 PR

回到原仓库，点 **Pull requests → New pull request**，选上你的 fork 和分支，填个标题（例如 `feat(dicts): 新增旅行词汇词库`），提交。

CI 会自动跑起来，**全绿就可以等审核**。

## 四、本地校验（推荐，能省一轮来回）

装了 Node 和 Git 的话，提交前先在本地跑一遍，CI 会报什么你现在就能看到。

```bash
npm install     # 第一次才需要
npm run verify  # 等价于 node scripts/verify-data.mjs
```

全通过时最后一行是：

```text
✓ 全部通过：17 个词库 / 51822 词条 / 75 篇文章
```

有失败项时退出码为 1，并逐条列出问题，例如：

```text
✗ 自检失败，共 1 项：
  - [my-travel-words] 词条仅 60，低于下限 100
```

**注意：`npm run verify` 校验的是 `public/dicts/` 下的真实文件。** 所以想本地预检，得先把文件放进 `public/dicts/`、把 meta 挂进 `index.json`。只是为了试一下格式的话，记得事后删干净，别把测试文件留在仓库里。

常用命令：

```bash
npm run typecheck  # 类型检查
npm run test       # 单元测试
npm run verify     # 词库与文章数据契约
```

CI（`.github/workflows/verify.yml`）跑的就是这三样加上 `npm ci`。

## 五、常见被拒原因

按实际发生频率排序。提交前对着查一遍。

| 原因                         | 症状                                         | 怎么改                                                                |
| ---------------------------- | -------------------------------------------- | --------------------------------------------------------------------- |
| **许可不明**                 | CI: `source 未标注 MIT 许可`                 | 按 2.2 写清出处 + `(MIT)`，用**半角**括号                             |
| **少了 Qwerty Learner 声明** | CI: `source 未标注来源`                      | `source` 里要含 `qwerty learner`（见 2.2）                            |
| **`count` 与实际不符**       | CI: `count 不符：words=120 meta.count=118`   | 改成 `words` 数组的真实长度，加词删词后务必同步                       |
| **词条数不足 100**           | CI: `词条仅 60，低于下限 100`                | 补足，或改为给现有词库补释义 / 例句                                   |
| **有重复词**（大小写不敏感） | CI: `重复单词 3 条`                          | `Apple` 和 `apple` 算重复，只留一条                                   |
| **释义为空**                 | CI: `空释义 5 条`                            | `t` 不能是空串或纯空格                                                |
| **单词首尾带空格 / 含换行**  | CI: `非法单词 2 条`                          | `w` 用 trim 后的值；一条一行，别粘多行                                |
| **音标格式不对**             | CI: `音标格式不合规 12 条`                   | `p` 必须形如 `/…/`；拿不准就整个字段删掉                              |
| **`id` 和文件名不一致**      | CI: `meta.id=xxx 与文件名不一致`             | 两边改成完全一样                                                      |
| **`meta` 多字段或少字段**    | CI: `meta 字段应为 …，实际 …`                | 只保留 2.1 表里那六个字段，别加 `author` / `version` 之类的自定义字段 |
| **索引与文件 meta 不一致**   | CI: `banks[xxx] 与单文件 meta 不一致`        | 从文件里复制粘贴到 `index.json`，别手打                               |
| **`category` 写错**          | CI: `category 非法：cet4`                    | 只能是 `exam` / `programming` / `basic`                               |
| **词根碎片混进词表**         | 人工审核退回：`-able`、`re-`、`un-` 这类片段 | 词库里只放**完整单词**。词缀片段对练习无意义，会干扰拼写训练          |
| **音标串混进释义**           | 人工审核退回：`t` 里出现 `/ˈbɔːrdɪŋ/`        | 音标放进 `p`，释义里只留中文                                          |
| **整段词典释义直接倒进来**   | 人工审核退回：`t` 长达几百字                 | 精简到 1–2 行，多义项用 `；` 分隔                                     |

> 「CI 报错」和「人工退回」是两回事。CI 只查机器能查的格式问题；词条质量、许可真实性、是否和现有词库高度重复，由维护者人工判断。

## 六、不想用 GitHub？

在 [Issues](https://github.com/2327192084/englishmate/issues) 里用中文写清词库名、词条数、来源许可，把 JSON 贴在正文的代码块里就行。维护者会帮你整理成 PR。

App 里的「提交到 GitHub」按钮做的就是这件事：它把标题、正文、以及「请把导出的 JSON 文件内容粘贴在下面」的提示都填好了。
